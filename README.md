# rss-hub · RSS 聚合头条

> 当前版本 **v1.7.3**（版本历史见 [CHANGELOG.md](CHANGELOG.md)）
>
> **专为 [Dot (Quote/0)](https://dot.mindreset.tech/docs/quote_0) 墨水屏设备开发**——
> 一款基于 ESP32-C3 的 2.13 寸黑白墨水屏桌面设备。输出按它的真实显示链路做过专门适配：
> 标题转纯文本（摘掉 emoji / 装饰符号，避免墨水屏豆腐块）、标题只留屏上显示得下的 13 全角字、
> 余下原文接进 `<description>` 正文、字段极简化。完整版 `feed.xml` 同时兼容任意标准 RSS 阅读器。

把几十个 RSS 源的**最新 5 条**抓下来，跨源去重、按发布时间倒序**取最新 120 条**（正文全文不截断），
合成一个新的 RSS，
由 **GitHub Actions** 定时重建、**GitHub Pages** 对外发布。全程免费、无需服务器、无需本机常开，
**不调用任何需要密钥的接口**。

```
feeds.txt ──► build_feed.py ──► docs/feed.xml ──► GitHub Pages ──► RSS 阅读器（完整版）
（源清单）    （Actions 里跑）        │
                                    └──────────► 树莓派（Pi/）──► moreaix.com ──► Dot 设备（设备版，一条一轮播）
```

**两份产物、两条发布链路**：GitHub Actions 只发**完整版** `feed.xml`；
**设备版** `feed-wrap.xml` 由树莓派上的 `Pi/rotate_screen.py` 每 5 分钟选一条写出来，发布在
`moreaix.com/rss/`（GitHub 不再发这一份，旧地址已 404）。抓取与显示是**两条独立时间线**，
细节见 [Pi/README.md](Pi/README.md)。

## 工作方式

1. **日常抓取**由 `rss.yml` 负责：每天 **3 次**（北京 08:00 / 13:00 / 18:00，UTC `0 0,5,10`）。
   `minute.yml`（作业内连跑 13 轮 × 5 分钟）与 `nightly.yml` 的**定时都已停用**——
   GitHub 的 cron 在这台仓库兑现率太低（实测 12 小时只给 4 档），留着反而制造「设计 5 分钟、实际 3 小时」的错觉；
   需要临时高频时用 `workflow_dispatch` 手动触发 `minute.yml`（跑完一轮循环约 58 分钟）。
2. 每轮：并发抓 49 源 × 5 条（约 40 秒）→ 生成**完整版** `docs/feed.xml` → 打包 `docs/` → 部署到 Pages。
   设备版不在这里生成（见文首「两条发布链路」）。
3. 每源取**最新 5 条**（49 × 5 = 245 条）→ **按发布时间倒序** → 跨源去重（同题保留最靠前的那条，
   也就是**最新**的一条）→ 截取最新 120 条进完整版（`ITEM_LIMIT`）。
   设备端轮播池同样是最新 120 条（`ROTATE_POOL_MAX`）：两个参数各管一头、现取同值 ——
   只调 `ITEM_LIMIT` 不会改变上屏节奏。
4. 跨源两道去重，命中任一条即丢弃：
   - **链接**：去掉 `#` 锚点与 `utm_*` / `from` / `spm` 这类**追踪参数**后比对，参数顺序也不影响身份
     （`?a=1&b=2` 与 `?b=2&a=1` 是同一条）；**有意义的查询参数必须保留** ——
     整段砍掉会把 `…?uid=3&pid=741` 这种「id 写在查询串里」的整站条目折叠成一条（RTI 实测从 5 条掉到 1 条）；
   - **标题**：去电头、去标点空白（**保留数字与字母**）取前 40 字，且**须 ≥ 8 字**（`DEDUP_TITLE_MIN`）才参与比较
     （否则「港股收盘」「主力资金流向」这类栏目型短标题会被误杀 —— 门槛降到 6 实测一条都没多丢，
     只多出一类误并，所以维持 8）。数字必须留着：「30日上涨」和「31日上涨」是两条新闻。
5. 某源这轮抓不到：立即重试一次 → 仍失败就用上一份 `feed.xml` 里该源的条目顶上（保留原 `pubDate`，
   排序位置不变），单源抖动不会让整份 feed 少一条。
6. 每天把 `docs/feed.xml` 备份提交一次（判断依据是「最后一次提交是不是今天」，当天第一档跑起来的那轮负责提交）：
   仓库里的 feed 只是镜像，权威副本是 Pages 上那份，备份只为 Pages 挂了还能从 git 取回；
   一天一条，历史不会被高频发布刷屏。

`guid` 用「文章链接|源地址」：同一篇文章被两个源同时收录时 guid 仍不同，阅读器不会吞条目。
设备版则把 guid 换成该串的 12 位 md5——它同时是轮播判断「这条是否已展示」的键。

## 轮播：屏幕怎么决定下一条播什么

云端只渲染 feed 里的**第一条**。如果照时间倒序整份发出去，屏幕就永远停在最新那条，
其余 100 多条一辈子轮不到。所以设备版 `feed-wrap.xml` 每版只发一条，选谁由 `rotate.json` 的标注决定
（这一条规则不承诺「每条都轮到」—— 覆盖率的上限来自「每窗只播 1 条」，见下面的「代价」）。

> **谁在跑这套规则**：`Pi/rotate_screen.py`，由树莓派上的 `rss-rotate.timer` 全天每 5 分钟拉起一次。
> 它**不联网、不抓源**，只读 `feed.xml`（池子）+ `rotate.json`（游标），选一条写 `feed-wrap.xml`。
> 抓取（`rss-build.timer`）与显示（`rss-rotate.timer`）是两条时间线 —— 以前选条写在抓取里，
> 于是「夜里抓取一小时一次」直接变成「屏幕一小时才换一条」。规则本身在 `rotate.py`，两处共用同一份实现。

```
每窗锚定当前时间窗：播「全池还没标注过的最新一条」，并把它的 guid 记进 shown
    —— 有新内容就播新的；没有才往旧里找（不设年龄上限）
全池都播过 → 清掉所有标注，从池子最新的一条重新开始一轮（cycle + 1）
w = now // 300  同一时间窗内重复构建不推进（幂等，多跑几轮也不跳条）
```

| 诉求 | 实现 |
|---|---|
| 最新先播 | 每窗都从「现在」往回找，而不是沿着一张开轮时拍好的清单往下走 |
| 每条都有一次机会 | 按**条**轮：同一时间窗里到达的多条各有一票，不再抢「代表位」 |
| 标记不会错位 | `shown` 存的是 **guid**，不是片号、也不是「池子里第几条」—— 池子每窗都在滚动，只有身份稳定 |
| 延迟不随时长增长 | 锚定当前窗，`back`（落后最新几条）稳态 0~1 条；新条目下一窗就能上屏 |
| 不重播 | 每条一轮只播一次；同一窗内重跑不推进；重开一轮时跳过刚上屏那条 |
| 不设年龄上限（**刻意**） | 没有新内容就播池子里最新的未播条，多旧都播 —— 墨水屏上「停住不动」和「坏了」分不出来（代价见下） |
| 全部播完才回头 | 全池都进过 `shown` 才清标记、从最新一条重来 |
| 未来时间戳不霸屏 | 发布时间晚于当前窗的条目不参与选条（源时钟错乱时屏不会被它独吞，见下） |
| 后台多跑几轮不跳条 | 用「时间窗」而不是「第几轮」做幂等键；重跑、手动触发、作业重叠都不推进 |
| 同前缀不连播（1.7.1 起） | 最近 3 窗出现过的**屏显串**（标题前 13 字）会被避开 —— 不同新闻截到 13 字可能一模一样。被跳过的仍是「未标注」，往后挪最多 3 窗（15 分钟），内容不丢（见下） |

**一句话说清规则**：已显示的标注起来，每窗重新播「最新的、还没标注的那一条」。
屏幕因此总跟着「现在」走 —— 有新内容就播新的；没有才往旧里找；池子全播完才清标注重来。

**还有一层观感约束（1.7.1）**：云端只渲染第一行，两条毫无关系的新闻截到屏上那 13 个字可能
一模一样（线上实测：同一栏目稿四连发、「CFTC：截至…」三连发）。所以选条时会避开最近 3 窗
（`RECENT_MAX`）出现过的屏显串 —— **这不是内容去重**，被跳过的条目不写 `shown`，仍是未标注，
稍后照常上屏，最多往后挪 3 窗（15 分钟；同一个显示串之间的实际最小间隔是 4 窗 = 20 分钟）。
候选全被挡住时退回最新那条，宁可连播也不空屏。

**为什么标记录 guid、而不是片号（1.7.0 的规则变更，理由写清楚）**：
1.4.0 ~ 1.6.x 把池子按 `ROTATE_SECONDS` 切成时间片、**片内只取最新一条当代表**、`shown` 记片号。
缺陷是同一片里后到的条目既拿不到代表位、也永远不会被标注，等于进池即弃 ——
实测池子 120 条只切出 26~44 片，一天里大半条目从未获得上屏机会，与「防止老条目轮不到」的
初衷正好相反。而无论记「片号」还是「池子里第几条」，池子一滚动都会错位：屏上第 3 条这一窗
是 A、下一窗就变成 B，等于把 B 的票记到 A 账上。guid 跟着条目身份走，滚到哪都不会错。
代价这条保持不变：产能是消费的十几倍，按条「取最新未播」依然偏向新内容 —— 但每条入池即进
候选队列，只要在被挤出池子之前排到，就一定会上屏一次。

**`ROTATE_MAX_LAG` 已经删掉了（它从来没生效过）**：曾经有个参数想把选择拆成「先看最近 6 片里
没播过的，取不到才放宽到全池」。但第二级是更大的集合、又同样取最新的那一个 —— 只要第一级非空，
两级必然挑中同一条；第一级为空时第二级给的就是第一级本该给的那条。所以它从未改变过任何结果：
`0` / `1` / `6` / `24` 跑同一条 24 小时仿真，指标逐项相同；直接调选择函数穷举 5 万组状态，
零反例。留着它只会让排障的人对着一个假旋钮调半天，所以连环境变量一起删了。

**代价（实测，不是估计）**：规则里**没有年龄上限**，低产能时就真的会播很旧的条目 ——
连续几个窗没有新内容时，`back` 会一路涨到把池子走空为止；好在按条轮之后存货不用排队，
同一份仿真里最差延迟从按片轮的 **4.4 小时**降到 **0.7 小时**（6 种子均值，见下）。

**覆盖率的物理上限（不是 bug）**：设备池 120 条（`ROTATE_POOL_MAX`）、每 5 分钟只播 1 条，
而各源每 5 分钟产出十几条 —— 消费能力只有产出的三分之一左右。所以设备版**只看最新**，
队尾那批会在排到之前被挤出池子（仿真覆盖率 **34%**，与按片轮时代的 32% 同水位）。
这是墨水屏「5 分钟一条」的物理上限，不是遗漏；想让旧条目也轮到，需要「按比例插播旧内容」
这类新机制 —— 调参数没用。

日常节律下的实测（`python tools/sim_rotate.py` 默认跑 6 个种子取均值：白天每窗 2.35 条按泊松抽样、
发布延迟摊满整窗、夜间积压摊满一小时）：中位 **2 分** · p90 **5 分** · 最差 **0.7 小时** ·
命中最新 **91%** · 覆盖率 **34%** · 播的是池子存货（落后 ≥2 条）占 **2%**。

和按片轮那阵的同一份仿真对比，换来的是双赢而不是「新鲜度换覆盖率」：

- 最差延迟 **4.4 小时 → 0.7 小时**，「播的是存货」的窗 **10% → 2%**，
  覆盖率 **32% → 34%**（同一水位）、中位延迟不变；
- 变的是「存货要不要排队」：以前同窗涌入的多条只有一条能出屏，其余要在下一轮重新争代表位，
  于是它们被反复往后推，尾巴就是这么堆到几小时的。

单种子方差仍然很大（最差在 20~70 分之间跳，取决于泊松的空窗簇落在哪），所以工具默认报
6 个种子的均值、**不要拿 p90 描述这条尾巴**：延迟分布里 6~60 分这一段几乎是空的，
多几个尾部窗就把 90 分位从 5 分推到几十分钟。可靠的是这两条：

- **92% 的上屏在 6 分内**；超过 30 分的几乎没有（6 种子均值约 0%）；
- 尾部来自**「本窗一条都没来」**：`--verbose` 打出的延迟最大 10 个窗全是这种时刻
  （泊松到达会成簇出现空窗，这个 5 分钟里各源都没发东西，屏幕要换内容就只能吃存货）。
  按条轮之后这条尾巴不再被片层放大 —— 存货不需要等同一片里的伙伴先播完。

**尾部不是夜间造成的**：夜间每小时灌 28 条、只播 1 条，所以早上池子是满的 —— 但白天它本来也一直是满的。
而且**夜间上屏本身是全天最健康的**（一小时才构建一次、每次抓回一小时的产出，「最新的未播条」总是刚发布的）。

想彻底压住尾部，唯一的办法是让空窗保持不动，但那样「屏幕停住」和「设备坏了」就分不出来了（见上面）。
调小 `ROTATE_POOL_MAX` 会缩短「可能被排挤掉的队尾」，代价是池子里的历史更少。

复盘工具：`python tools/sim_rotate.py`（24 小时仿真，输出新鲜度 / 覆盖率 / 上屏名次 / 落后条数四张表，
默认 6 个种子取均值；`--verbose` 打延迟最大的 10 个窗，`--seed=N` 固定种子复现别人的数）。

**未来时间戳的处理**：源把 `pubDate` 写到 2030 年（时区配错、服务器时钟漂移、模板拼错年份都会发生）时，
它永远排在队首，「取全池没播过里最新的一条」每窗都会选中它 —— 屏幕就被这一条霸占了。
现在改成「时间还没到就先不播」：发布时间晚于当前窗的条目不参与选条。代价是这种源的条目
**在设备版上一直不出现**（完整版 `feed.xml` 里仍照常列出），换来的是屏幕不被它独吞；
源把时间改对之后自然恢复。也不能改成「按抓取时刻算」—— 那样它的时间每窗重算、永远是最新的，
等于每窗都重播一次，比不钳更糟。

> **缓存这关已经绕开了（2026-10-30 起）**：设备版改由树莓派发布在 `moreaix.com/rss/`，
> Cloudflare 对该路径是 `cf-cache-status: DYNAMIC`（不缓存），Pi 的 `serve.py` 也发
> `Cache-Control: no-cache` —— 所以早期「Pages CDN `max-age=600` 导致同一条连显两次」的
> 现象不会再出现。**这条历史约束仅当有人把设备版搬回 Pages 时才需要重新考虑**
> （届时把 `ROTATE_SECONDS` 改成 600 是最省事的兜法）。

## 设备适配（Dot Quote/0）

**先看机制**（官方文档：[内容模式](https://dot.mindreset.tech/docs/quote_0/start/content_mode)、
[刷新时间](https://dot.mindreset.tech/docs/quote_0/faq/refresh_timing)、
[RSS](https://dot.mindreset.tech/docs/service/studio/rss_feed)）：

设备端（ESP32-C3，400 KB 内存）**不解析 RSS XML**。在 Dot App 里把 RSS 地址加进「循环内容」后，
由 **Dot 云端**抓取解析、按自家模板渲染成位图，设备按刷新间隔（App 里 1 分钟～12 小时可调）拉图显示。
**显示几条、字号多大、怎么排版全由云端决定**，订阅方控制不了；云端多久抓一次本源也由它调度，
但本源每 5 分钟重建一次，随时来抓都是当前该显示的那一条。

我们唯一能控制的，是「喂给云端的原料」：

| 项目 | 完整版 `feed.xml` | 设备版 `feed-wrap.xml` |
|---|---|---|
| 标题字符 | 原样（可含 emoji） | **纯文本**：emoji、箭头、几何图形、零宽字符、变体选择符全部摘除（黑白屏上是豆腐块或占位） |
| 标题长度 | 原样 | **只放屏上显示得下的 13 全角**，超出的字一个不丢，全部移入正文 |
| 正文 | 原 feed 的 `description` / `content:encoded` 摘要（默认不限，全文照发；设 `FEED_BODY_MAX` 可截断，尾端补 `…`） | `<description>` = 标题余文 + 原 feed 摘要（最多 90 全角，再长尾端补 `…`） |
| 条目数 | **最新 120 条**（按发布时间倒序后截取，`ITEM_LIMIT`=120；设 0 = 不限） | **只发 1 条**：轮播到的那条（云端只会渲染第一条，多给也用不上） |
| 字段 | title / link / pubDate / guid / source，channel 含 `atom:link`、`copyright`、`generator`、`ttl` | 同上 + description；guid 用 12 位短哈希，channel 去掉 `atom:link` / `generator` / `ttl` 三项，`copyright` 保留 |

**实测依据（2026-10-29，296×152 屏，真机截图）**

1. RSS 卡片的标题是**一行大字号**，13 个全角字正好顶格——「卡特彼勒第三季度电力与能源」占满整行，
   后面的字被云端直接切掉，并补上它自己的省略号；
2. 标题里塞换行符试过三种写法（`&#10;` / `<br>` / U+2028），云端**一律不认**，屏上永远只有一行。

宽度抢不回来，就往下要空间：标题只管放得下的 13 个字，余下原文写进 `<description>`，
让云端的正文区域接着排——一屏能读到的字数从 13 涨到 13 + 最多 90。

```xml
<title>卡特彼勒第三季度电力与能源</title>        <!-- 标题行：13 全角顶格，云端不会再切 -->
<description>业务营收同比增长12%</description>     <!-- 正文：标题装不下的原文，字不丢 -->
```

排版细节：

- 标题行**末尾不加 `…`**：正文紧接着就是原文，省略号只会白挤掉一个字；
- 正文**不以标点开头**（`，、；：。` 会被剥掉）——行首标点是中文排版大忌；
- 半角词不会被切一半：切点落在词中间时退到上一个空格（`Fed officials signal`，而不是 `…signal patie`）；
- 正文（标题余文 + 摘要原文）超过 `SCREEN_BODY_MAX`（默认 90 全角）才在尾端补 `…`。

**如果云端不渲染 `<description>`**，屏上仍然只有那 13 字标题，和改之前完全一样，不会更差。

**来源与版权**：每条都带 `<source url="源地址">源名</source>`（RSS 2.0 标准字段，Inoreader /
Feedly / NetNewsWire 都会读，多数还会在标题旁显示源名），`<link>` 直通原文，完整版的 `<guid>`
里另存「原文链接 | 源地址」。channel 一级还有一条 `<copyright>`：「内容版权归各来源媒体，
本站仅聚合标题与摘要，原文以各条 link 为准」——聚合别人的标题与摘要，这句得写明白。
设备屏上不显示源名（152 px 高、正文只有 4 行，挤不出位置），要看来源点开条目即可。
判断是否生效很简单：看标题后面有没有接着出现正文那句。
`SCREEN_LINE_WIDTH` / `SCREEN_BODY_MAX` 改工作流 `env:` 才能长期生效，参数说明见 [OPERATIONS.md#调参](OPERATIONS.md#调参)。

## 为什么不用 Dot 文本 API

Dot 还有一个文本 API（`POST /api/authV2/open/device/{id}/text`），版面固定「标题 1 行 + 正文 3 行 + 落款」，
字号行高可调，理论上能一屏 4 条。早期版本接入过，之后**主动下线**，原因只有一个：

- 它要求在 Dot App 里新建 API 密钥（`dot_app_…` 开头），并把**设备序列号**一起交给调用方；
- 之后每一轮采集都要带着这个密钥向设备发起一次写请求。

这个密钥等同于设备写权限。一旦落到仓库、CI 日志或第三方 runner 上，就等于把设备控制权交了出去。
本项目的立身之本是**零凭证**，多一屏几条的收益不值得长期背一个能直接控制设备的口令。
现在只走 RSS 这一条只读通路：不发起任何写请求，仓库里没有任何密钥；
`tools/check_secrets.py` 把 `dot_app_…` 形态也列进了拦截规则。

## 加一个源

```text
# 财联社·电报滚动
https://feed.quanwenrss.com/feed/cailianshe-roll.xml
```

注释行成为条目里的 `<source>` 源名，建议写成「媒体名·栏目」；括号里的备注会被剥掉。
改完 push 就自动重建。批量验证新源能否抓通，本地跑一遍只看 `[失败]` 行：

```bash
python3 build_feed.py
```

## 已知限制

- **GitHub 的 cron 会延迟和丢档，这台仓库尤其低频**：实测 12 小时只兑现 **4 档**（预期 ~144 档）、
  开始时间偏移 15~46 分钟、多数整点直接跳过。所以 5 分钟/每小时的节拍**已经停用**，
  日常改成 `rss.yml` 每天 3 次（北京 08/13/18）——这是「设计值 ≈ 承诺值」的折中。
  真要做到 5 分钟一版只有两条路：挂外部定时器 dispatch（见
  [OPERATIONS.md#10-定时任务完全不触发](OPERATIONS.md#10-定时任务完全不触发)），
  或者像树莓派那样用自己的 timer 抓（`Pi/services/rss-build.timer`，已这么做）；
- **Pages 传统构建有 10 次/小时软限制**，每分钟一次会被限流；本项目改用自定义 Actions 部署
  （`build_type: workflow`），官方文档明确该限制不适用于这种构建方式；
- **runner 占用**：现在每天 3 次、每次约 40 秒，可忽略；若手动 dispatch `minute.yml` 会跑满约 58 分钟；
- 设备端「5 分钟换一条」说的是**轮播节拍**（树莓派 `rss-rotate.timer`），不是产出入库速度：
  池子里 120 条可播，池子换血靠上面抓到的新条目；
- `github.io` 在部分网络环境访问偏慢，可用上面两个镜像（跟随仓库备份，每天更新一次）；
- 正文能否显示取决于 Dot 云端是否渲染 `<description>`，不受本项目控制；不渲染时退化为 13 字标题。

## 开发与审查

改动代码前后跑这三条，全绿再提交（完整标准见 [CODE_REVIEW.md](CODE_REVIEW.md)）：

```bash
python3 -m unittest discover -s tests -v    # 单测：178 个用例（含分层契约、行为基线、轮播边界、清洗边界、门禁自检）
python3 tools/review_check.py               # 审查门禁：文件/函数超限、裸 except、生成物漂移、文档脱节、版本号
python3 tools/check_secrets.py              # 凭据扫描
```

行为基线是这套流程的核心：`tests/golden.txt` 存着渲染层在固定输入上的逐字节输出，
任何「顺手改了排版」的改动都会被 `test_golden` 抓住。确实要改排版时：

```bash
python3 tools/golden_snapshot.py --write    # 更新基线
# 并在 CHANGELOG.md 写清改了什么、为什么 —— 否则下次没人知道这条 baseline 是被谁动了
```

四条铁律（都是踩过坑换来的）：

1. **不手改生成文件**：`minute.yml` 由脚本生成、`tests/golden.txt` 由快照脚本生成，
   改结构请改脚本后重新生成（门禁会比对，手改必红）；
2. **手动 dispatch 了 `minute.yml`（58 分钟循环）时，改代码前先取消它**，再重新 dispatch——
   作业只在每小时首轮 `git pull` 一次，所以整点内推送的代码最长要等 60 分钟才被它用上，
   这期间每一轮都拿旧代码重新构建并覆盖 Pages（线上版本串被写回旧值就是这么来的）。
   **日常的 `rss.yml` 是一次性作业（约 40 秒），不存在这个问题**，不用取消；
   取消方式（网页按钮 / `gh run cancel` / 一次 API 调用）见 `OPERATIONS.md` §16；
3. **改参数必须同步 `OPERATIONS.md` 的参数表**，门禁会检查代码里的每个环境变量是否在文档中出现过；
4. **发版必须三件套**：`version.py` 加版本号 → `CHANGELOG.md` 记一条 → 页面页脚跟上，
   门禁会检查 README / OPERATIONS / 两个页面上有没有出现当前版本号。

## 凭证与安全

**仓库里不含任何 token、口令或私钥**，克隆下来直接跑，不需要填任何东西。

- `.gitignore` 屏蔽 `*.env` / `.env*` / `*.pem` / `*.key` / `id_rsa*` 等；
- `tools/check_secrets.py` 可随时自查：`python3 tools/check_secrets.py`；
- `.github/workflows/review.yml` 每次推送 / PR 自动跑「凭据 + 语法 + 单测 + 审查规则」四道关卡，
  混进真 token 或违反 CODE_REVIEW.md 的硬规则都会让构建失败。

|---|---|
