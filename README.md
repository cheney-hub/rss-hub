# rss-hub · RSS 聚合头条

> 当前版本 **v1.3.0**（版本历史见 [CHANGELOG.md](CHANGELOG.md)）
>
> **专为 [Dot (Quote/0)](https://dot.mindreset.tech/docs/quote_0) 墨水屏设备开发**——
> 一款基于 ESP32-C3 的 2.13 寸黑白墨水屏桌面设备。输出按它的真实显示链路做过专门适配：
> 标题转纯文本（摘掉 emoji / 装饰符号，避免墨水屏豆腐块）、标题只留屏上显示得下的 13 全角字、
> 余下原文接进 `<description>` 正文、字段极简化。完整版 `feed.xml` 同时兼容任意标准 RSS 阅读器。

把几十个 RSS 源的**最新 5 条**抓下来，跨源去重、按发布时间倒序（默认不限条数，全部进 feed），
合成一个新的 RSS，
由 **GitHub Actions** 定时重建、**GitHub Pages** 对外发布。全程免费、无需服务器、无需本机常开，
**不调用任何需要密钥的接口**。

```
feeds.txt ──► build_feed.py ──► docs/feed.xml       ──► GitHub Pages ──► RSS 阅读器
（源清单）    （Actions 里跑）   docs/feed-wrap.xml                    ──► Dot 设备（标题＋正文）
```

## 工作方式

1. `.github/workflows/minute.yml` 在北京时间 **06:00–23:59** 每小时 :07 触发，作业内连跑 13 轮
   （对齐到 :10 :15 … :55 :00 :05）；`nightly.yml` 在 **00:00–05:59** 每小时跑一轮。
2. 每 5 分钟一轮：并发抓 49 源 × 5 条（约 40 秒）→ 生成两份 feed → 打包 `docs/` → 部署到 Pages → 对齐到下一个 5 分钟整点。
3. 每源取**最新 5 条**，跨源去重后按时间倒序全部进完整版（默认不限条数）——池子够大，回补旧片时才有内容可播；
   设备端轮播池另行取**最新 120 条**（`ROTATE_POOL_MAX`）。
4. 跨源两道去重，命中任一条即丢弃：
   - **链接**：去掉 `#` 片段与 `?` 参数再比，规避 `?utm_source=` 造成的伪重复；
   - **标题**：去标点空白、只留汉字取前 20 字，且**须 ≥ 8 字**才参与比较（否则「港股收盘」这类短标题会被误杀）。
5. 某源这轮抓不到：立即重试一次 → 仍失败就用上一份 `feed.xml` 里该源的条目顶上（保留原 `pubDate`，
   排序位置不变），单源抖动不会让整份 feed 少一条。
6. 每 10 轮把 `docs/feed.xml` 备份提交一次，仓库历史不会因高频发布而膨胀。

`guid` 用「文章链接|源地址」：同一篇文章被两个源同时收录时 guid 仍不同，阅读器不会吞条目。
设备版则把 guid 换成该串的 12 位 md5——它同时是轮播判断「这条是否已展示」的键。

## 轮播：屏幕怎么决定下一条播什么

云端只渲染 feed 里的**第一条**。如果照时间倒序整份发出去，屏幕就永远停在最新那条，
其余 100 多条一辈子轮不到。所以设备版 `feed-wrap.xml` 每版只发一条，选谁由 `docs/rotate.json` 的标记决定
（注意：这一条规则**不追求「每条都轮到」**，覆盖率的上限只有三分之一，原因见下面的「代价」）：

```
把池子按「5 分钟」切成时间片，每片取最新一条当代表
每窗锚定当前时间窗：播「全池没播过里最新的一片」，记进 shown
    —— 池子里最新的一片通常就是当前窗的，所以屏幕总跟着「现在」走
全池都播过 → 清掉所有标记，从池子最新的片重新开始
w = now // 300  同一时间窗内重复构建不推进（幂等，多跑几轮也不跳条）
```

| 诉求 | 实现 |
|---|---|
| 最新先播 | 每窗都从「现在」往回找，而不是沿着一张开轮时拍好的清单往下走 |
| 延迟不随时长增长 | 锚定当前窗，`lag` 中位 1 片、白天几乎每窗都有新内容可播；新条目下一窗就能上屏 |
| 不重播 | 每个片只播一次，`shown` 记片号；同一窗内重跑不推进 |
| 不设年龄上限（**刻意**） | 没有新内容就播池子里最新的未播片，多旧都播 —— 墨水屏上「停住不动」和「坏了」分不出来（代价见下） |
| 全部播完才回头 | 全池都进过 `shown` 才清标记、从最新的片重来 |
| 未来时间戳不霸屏 | 片号晚于当前窗的片不参与轮播（源时钟错乱时屏不会被它独吞，见下） |
| 后台多跑几轮不跳条 | 用「时间窗」而不是「第几轮」做幂等键；重跑、手动触发、作业重叠都不推进 |

**为什么按「时间片」而不是按「条」**：每 5 分钟各源新产出十几条，屏幕 5 分钟只放得下 1 条 ——
产能是消费的十几倍。按条取「未显示里最新的一条」的话，新条目永远比旧的新，每一窗都在追新，
池子里的老条目还没轮到就被设备池上限（`ROTATE_POOL_MAX`，120 条）挤出去（实测 120 条里 **0 条**上过屏）。
按片轮，一片只出一条代表，产出和消费才对得上。

**一句话说清规则**：每窗播「池子里还没播过、最新的一片」。屏幕因此总跟着「现在」走 ——
有新内容就播新的；没有才往旧里找；池子全播完才清标记重来。

**`ROTATE_MAX_LAG` 已经删掉了（它从来没生效过）**：曾经有个参数想把选择拆成「先看最近 6 片里
没播过的，取不到才放宽到全池」。但第二级是更大的集合、又同样取最新的那一个 —— 只要第一级非空，
两级必然挑中同一条；第一级为空时第二级给的就是第一级本该给的那条。所以它从未改变过任何结果：
`0` / `1` / `6` / `24` 跑同一条 24 小时仿真，指标逐项相同；直接调选择函数穷举 5 万组状态，
零反例。留着它只会让排障的人对着一个假旋钮调半天，所以连环境变量一起删了。

**代价（实测，不是估计）**：上面的规则里**没有年龄上限**，低产能时就真的会播很旧的片 ——
各源全停 2 小时 → `lag` 36 片（3 小时）；0.4 条/窗的极端场景，上屏内容最旧到过 **22.9 小时**；
日常节律下仿真 `lag` 最大 53 片（4.4 小时）。这是刻意交换的：墨水屏不显示时间戳，
「屏幕停住」和「设备坏了」在用户眼里是同一件事，「一条 20 小时前的旧闻」至少还证明设备活着。

**覆盖率的物理上限（不是 bug）**：设备池 120 条（`ROTATE_POOL_MAX`）、每 5 分钟只播 1 条，而各源每 5 分钟产出十几条 ——
消费能力只有产出的三分之一左右。所以设备版**只看最新**，旧条目会随设备池上限被挤掉、
从头到尾没上过屏（仿真里约 2/3 抓回来的条目从未上屏，覆盖率 32%）。这是墨水屏「5 分钟一条」的
物理上限，不是遗漏。想把旧条目也轮到，需要「按比例插播旧内容」这类新机制 —— 调参数没用。

日常节律下的实测（`python tools/sim_rotate.py` 默认跑 6 个种子取均值：白天每窗 2.35 条按泊松抽样、
发布延迟摊满整窗、夜间积压摊满一小时）：中位 **2 分** · p90 **7 分** · 最差 **4.4 小时** ·
命中最新 **90%** · 覆盖率 **32%** · 播的是旧片（落后 ≥2 片）占 10%。

单种子方差很大，所以工具默认报 6 个种子的均值。**但不要用 p90 描述这条尾巴** —— 延迟分布在
6~60 分之间几乎是空的（只占 3%），90 分位正好落在这条缝上，单种子于是在 4~60 分之间乱跳，
写任何一个单值都会误导。可靠的是这三条（20 种子口径）：

- 中位 **1.5 分**，**90% 的上屏在 6 分内**；
- 约 **7~9%** 的上屏在 30 分以上，这一批的中位约 **2.5 小时**（20 种子 147~153 分）；
  **99.7% 发生在「该窗没有任何新内容」的时刻**（泊松到达会成簇出现空窗，这个 5 分钟里各源都没发东西，
  屏幕要换内容就只能从池子存货里挑）。剩下 0.3% 是另一种情形：新条目恰好都落进**已经播过的片号**
  （每窗约 0.8% 概率，`2.35 条 ÷ 300 秒片长`），本窗虽有新内容却没有「新的未播片」；
- 最差 **4~6 小时**。这个上界不是机制设的年龄上限，而是**设备池容换算成时间**：
  设备池 120 条（`ROTATE_POOL_MAX`）÷ 每窗 2.35 条 = 51 个时间片 ≈ **4.3 小时**（实测 6 种子均值 4.35 小时，
  20 种子最大 5.9 小时，簇发时更接近上界）。
  **为什么上界由 `ROTATE_POOL_MAX` 决定而不是 `ITEM_LIMIT`**：1.3.0 起 `ITEM_LIMIT` 默认 0（完整版不限条数），
  池子真正进入轮播的那部分被 `ROTATE_POOL_MAX` 钉在最新 120 条 —— 决定「最差滞后」的是设备池的深度
  （池条数 ÷ 每窗新增 ≈ 片数），完整版多出来的条目根本不参与轮播。**按旧文档去调 `ITEM_LIMIT` 不会再改变这个上界**；
  要压尾部就调小 `ROTATE_POOL_MAX`。

**尾部不是夜间造成的**：夜间每小时灌 28 条、只播 1 条，所以早上池子是满的 —— 但白天它本来也一直是满的。
实测「池底年龄」下午（中位 284 分）比早上（257 分）还深。而且**夜间上屏本身是全天最健康的**
（中位 1.6 分、最大 13 分），因为夜间一小时才构建一次、每次抓回一小时的产出，「最新的未播片」总是刚发布的。

想压住尾部，唯一的办法是让空窗保持不动，但那样「屏幕停住」和「设备坏了」就分不出来了（见上面的代价）。
反过来，把 `ROTATE_POOL_MAX` 调小会直接缩短这个上界 —— 它是唯一能调的量，代价是池子里的历史更少。

另一条路是「没新内容就重播最新的几条」，能把 `lag` 压住，但会打破「一轮内每条只播一次」：
覆盖率更低、屏幕上反复出现同一条，所以没走。想真正限制「最旧能播到多旧」，就得走这条路。

复盘工具：`python tools/sim_rotate.py`（24 小时仿真，输出新鲜度 / 覆盖率 / 上屏名次 / 落后片数四张表，
默认 6 个种子取均值；`--verbose` 打延迟最大的 10 个窗，`--seed=N` 固定种子复现别人的数）。
池 120 条（`ROTATE_POOL_MAX`）≈ 51 个时间片。

**未来时间戳的处理**：源把 `pubDate` 写到 2030 年（时区配错、服务器时钟漂移、模板拼错年份都会发生）时，
它的片号永远最大，「取全池没播过里最新的一片」每窗都会选中它 —— 屏幕就被这一条霸占了。
现在改成「时间还没到就先不播」：片号晚于当前窗的片不参与轮播。代价是这种源的条目
**在设备版上一直不出现**（完整版 `feed.xml` 里仍照常列出），换来的是屏幕不被它独吞；
源把时间改对之后自然恢复。也不能改成「按抓取时刻算」—— 那样它的片号每窗重算、永远是最新的，
等于每窗都重播一次，比不钳更糟。

> **已知硬约束**：GitHub Pages 的 CDN 缓存是 `max-age=600`（实测响应头）。
> 5 分钟一版时，设备有可能拿到 10 分钟前的旧版本，出现「同一条连显两次、中间那条没看到」。
> 真机上如果出现这现象，把 `ROTATE_SECONDS` 改成 `600`（10 分钟一条），节奏放慢但绝不漏。

## 设备适配（Dot Quote/0）

**先看机制**（官方文档：[内容模式](https://dot.mindreset.tech/docs/quote_0/start/content_mode)、
[刷新时间](https://dot.mindreset.tech/docs/quote_0/faq/refresh_timing)、
[RSS](https://dot.mindreset.tech/docs/service/studio/rss_feed)）：

设备端（ESP32-C3，400 KB 内存）**不解析 RSS XML**。在 Dot App 里把 RSS 地址加进「循环内容」后，
由 **Dot 云端**抓取解析、按自家模板渲染成位图，设备按刷新间隔（App 里 1 分钟～12 小时可调）拉图显示。
**显示几条、字号多大、怎么排版全由云端决定**，订阅方控制不了；云端多久抓一次本源也由它调度，
但本源每 5 分钟重建一次，随时来抓都是当前该显示的那一条。

我们唯一能控制的，是「喂给云端的原料」：

| 项目 | 完整版 `feed.xml` | 设备版 `feed-wrap.xml` |
|---|---|---|
| 标题字符 | 原样（可含 emoji） | **纯文本**：emoji、箭头、几何图形、零宽字符、变体选择符全部摘除（黑白屏上是豆腐块或占位） |
| 标题长度 | 原样 | **只放屏上显示得下的 13 全角**，超出的字一个不丢，全部移入正文 |
| 正文 | 原 feed 的 `description` / `content:encoded` 摘要（默认不限，全文照发；设 `FEED_BODY_MAX` 可截断，尾端补 `…`） | `<description>` = 标题余文 + 原 feed 摘要（最多 90 全角，再长尾端补 `…`） |
| 条目数 | 默认不限（去重后的全部条目；设 `ITEM_LIMIT` 可按时间砍最旧） | **只发 1 条**：轮播到的那条（云端只会渲染第一条，多给也用不上） |
| 字段 | title / link / pubDate / guid / source，含 `atom:link`、`generator`、`ttl` | 同上 + description；guid 用 12 位短哈希，channel 去掉上述三项 |

**实测依据（2026-10-29，296×152 屏，真机截图）**

1. RSS 卡片的标题是**一行大字号**，13 个全角字正好顶格——「卡特彼勒第三季度电力与能源」占满整行，
   后面的字被云端直接切掉，并补上它自己的省略号；
2. 标题里塞换行符试过三种写法（`&#10;` / `<br>` / U+2028），云端**一律不认**，屏上永远只有一行。

宽度抢不回来，就往下要空间：标题只管放得下的 13 个字，余下原文写进 `<description>`，
让云端的正文区域接着排——一屏能读到的字数从 13 涨到 13 + 最多 90。

```xml
<title>卡特彼勒第三季度电力与能源</title>        <!-- 标题行：13 全角顶格，云端不会再切 -->
<description>业务营收同比增长12%</description>     <!-- 正文：标题装不下的原文，字不丢 -->
```

排版细节：

- 标题行**末尾不加 `…`**：正文紧接着就是原文，省略号只会白挤掉一个字；
- 正文**不以标点开头**（`，、；：。` 会被剥掉）——行首标点是中文排版大忌；
- 半角词不会被切一半：切点落在词中间时退到上一个空格（`Fed officials signal`，而不是 `…signal patie`）；
- 正文（标题余文 + 摘要原文）超过 `SCREEN_BODY_MAX`（默认 90 全角）才在尾端补 `…`。

**如果云端不渲染 `<description>`**，屏上仍然只有那 13 字标题，和改之前完全一样，不会更差。
判断是否生效很简单：看标题后面有没有接着出现正文那句。
`SCREEN_LINE_WIDTH` / `SCREEN_BODY_MAX` 改工作流 `env:` 才能长期生效，参数说明见 [OPERATIONS.md#调参](OPERATIONS.md#调参)。

## 为什么不用 Dot 文本 API

Dot 还有一个文本 API（`POST /api/authV2/open/device/{id}/text`），版面固定「标题 1 行 + 正文 3 行 + 落款」，
字号行高可调，理论上能一屏 4 条。早期版本接入过，之后**主动下线**，原因只有一个：

- 它要求在 Dot App 里新建 API 密钥（`dot_app_…` 开头），并把**设备序列号**一起交给调用方；
- 之后每一轮采集都要带着这个密钥向设备发起一次写请求。

这个密钥等同于设备写权限。一旦落到仓库、CI 日志或第三方 runner 上，就等于把设备控制权交了出去。
本项目的立身之本是**零凭证**，多一屏几条的收益不值得长期背一个能直接控制设备的口令。
现在只走 RSS 这一条只读通路：不发起任何写请求，仓库里没有任何密钥；
`tools/check_secrets.py` 把 `dot_app_…` 形态也列进了拦截规则。

```text
# 财联社·电报滚动
```

```bash
python3 build_feed.py
```

## 已知限制

- **GitHub 的 cron 最短 5 分钟，还会延迟和丢档**（实测新仓库 50 分钟内 0 次触发）——所以分钟级不靠 cron，
  靠「小时级 cron + 作业内自循环」；
- **Pages 传统构建有 10 次/小时软限制**，每分钟一次会被限流；本项目改用自定义 Actions 部署
  （`build_type: workflow`），官方文档明确该限制不适用于这种构建方式；
- **runner 占用**：白天 18 小时近乎连续（每小时 13 轮 ≈ 58 分钟）+ 夜间 6 次：公开仓库分钟数不计量，但属高频用法；
  想降载就改轮数（见 [OPERATIONS.md#刷新节奏](OPERATIONS.md#刷新节奏)）；
- 5 分钟档期间，每小时最后约 2 分钟是收尾空档；深夜则是整点之间的一小时空档；
- `github.io` 在部分网络环境访问偏慢，可用上面两个镜像（跟随仓库备份，约 10 分钟一次）；
- 正文能否显示取决于 Dot 云端是否渲染 `<description>`，不受本项目控制；不渲染时退化为 13 字标题。

## 开发与审查

改动代码前后跑这三条，全绿再提交（完整标准见 [CODE_REVIEW.md](CODE_REVIEW.md)）：

```bash
python3 -m unittest discover -s tests -v    # 单测：84 个用例（含分层契约、行为基线、轮播边界）
python3 tools/review_check.py               # 审查门禁：文件/函数超限、裸 except、生成物漂移、文档脱节、版本号
python3 tools/check_secrets.py              # 凭据扫描
```

行为基线是这套流程的核心：`tests/golden.txt` 存着渲染层在固定输入上的逐字节输出，
任何「顺手改了排版」的改动都会被 `test_golden` 抓住。确实要改排版时：

```bash
python3 tools/golden_snapshot.py --write    # 更新基线
# 并在 CHANGELOG.md 写清改了什么、为什么 —— 否则下次没人知道这条 baseline 是被谁动了
```

四条铁律（都是踩过坑换来的）：

1. **不手改生成文件**：`minute.yml` 由脚本生成、`tests/golden.txt` 由快照脚本生成，
   改结构请改脚本后重新生成（门禁会比对，手改必红）；
2. **改了 `build_feed.py` / `rotate.py` / `render.py` 要先取消正在跑的 `minute.yml` 作业**，
   再重新 dispatch——作业里的代码只在「备份轮」（`CYCLE % 10 == 1`，每 10 轮一次）`git pull`
   时才更新，其余每轮都拿那份旧代码重新构建并覆盖 Pages（线上版本串被写回旧值就是这么来的）；
   取消方式（网页按钮 / `gh run cancel` / 一次 API 调用）见 `OPERATIONS.md` §16；
3. **改参数必须同步 `OPERATIONS.md` 的参数表**，门禁会检查代码里的每个环境变量是否在文档中出现过；
4. **发版必须三件套**：`version.py` 加版本号 → `CHANGELOG.md` 记一条 → 页面页脚跟上，
   门禁会检查 README / OPERATIONS / 两个页面上有没有出现当前版本号。

## 凭证与安全

**仓库里不含任何 token、口令或私钥**，克隆下来直接跑，不需要填任何东西。

- `.gitignore` 屏蔽 `*.env` / `.env*` / `*.pem` / `*.key` / `id_rsa*` 等；
- `tools/check_secrets.py` 可随时自查：`python3 tools/check_secrets.py`；
- `.github/workflows/review.yml` 每次推送 / PR 自动跑「凭据 + 语法 + 单测 + 审查规则」四道关卡，
  混进真 token 或违反 CODE_REVIEW.md 的硬规则都会让构建失败。

## 版本

| 位置 | 怎么看 |
|---|---|
| 当前版本 | [version.py](version.py) 的 `__version__`，本页顶部与两个页面页脚同步显示 |
| 命令行 | `python3 build_feed.py --version` → `rss-hub 1.3.0` |

| 历史 | [CHANGELOG.md](CHANGELOG.md) |

版本号语义：主版本 = 输出格式变化（订阅端要跟着改）；次版本 = 新增能力或排版规则调整；
修订号 = 只修 bug，输出应逐字节不变（可用行为基线验证）。
